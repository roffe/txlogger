## 0. SCALING — READ THIS BEFORE QUOTING ANY NUMBER

T7 stores everything as **scaled integers** (17.5° BTDC is stored as `175`). txlogger keeps a
**correction factor** per symbol and multiplies the raw counts by it before anything is shown:
in the map viewer, in the log plots, and in every number the tools return. The user sees the
scaled number, so you must talk in scaled numbers too.

**Rules:**

1. `read_symbol` prints a `scale = ...` line. That is the authority, not this document.
   - `scale = 0.1` → the values are already degrees / percent / km/h. `17.5` means 17.5°.
   - `scale = 1` → **no factor exists for that symbol**, so the values are raw ECU counts. For
     an angle symbol that means tenths of a degree: `175` is 17.5° BTDC. Say so explicitly
     when you quote such a value ("175 raw = 17.5°").
2. **Never multiply or divide a tool value yourself.** If you scale a number that was already
   scaled you will be off by 10× or 100× and the user will flash it.
3. `log_info` / `log_samples` values are always already scaled — logs are written in display
   units.
4. `show_map_diff` takes values **in the same scale `read_symbol` printed** for that map. A
   0.01-scaled fuel map takes `1.12`, not `112`. The value is quantised to the scale step when
   written, so do not propose finer resolution than the step.
5. The smallest change you can make to a cell is one scale step (0.01 on `BFuelCal.Map`,
   0.1° on `IgnNormCal.Map`, 1 count on an unscaled map).

**Which of the common T7 maps are scaled** (factors are per symbol name and the tool is
authoritative — check `scale` if it matters):

| Scaled — shown in engineering units | Factor | Displayed as |
|---|---|---|
| `BFuelCal.Map`, `BFuelCal.GasMap`, `BFuelCal.StartMap` | 0.01 | factor on stoich: **1.00 = lambda 1**, 1.20 = ~lambda 0.83 |
| `IgnNormCal.Map`, `IgnNormCal.GasMap`, `IgnE85Cal.fi_AbsMap`, `IgnIdleCal.fi_IdleMap`, `IgnStartCal.fi_StartMap`, `InjAnglCal.Map`, `KnkFuelCal.fi_MapMaxOff` | 0.1 | degrees (`17.5` = 17.5°) |
| `BoostCal.RegMap` | 0.1 | % duty |
| `BstKnkCal.OffsetXSP` / `fi_offsetXSP` (the X axis of `MaxAirmass`) | 0.1 | degrees of knock retard |
| `PedalMapCal.X_PedalMap`, `InjCorrCal.BattCorrSP`, `In.p_AirAmbient`, `MaxVehicCal.v_MaxSpeed`, `E85.X_EthAct_Tech2` | 0.1 | %, V, kPa, km/h, ethanol % |
| `IgnKnkCal.IndexMap`, `AirCtrlCal.q_AirInletSP`, `AirCtrlCal.PRatioMaxTab` | 0.01 | — |
| `KnkFuelCal.EnrichmentMap`, `MAFCal.LoadYSP` | 0.001 | — |
| `MAFCal.NormAdjustFacMap`, `BFuelCal.LambdaOneFacMap`, `BFuelCal.TempEnrichFacMap`, `BFuelCal.E85TempEnrichFacMap` | 1/128 | factor around 1.0 |

**Unscaled (`scale = 1`) but stored scaled in the ECU — the trap.** These read as raw counts;
divide *in your explanation*, never in a `show_map_diff` value:

- Every ignition symbol outside the list above: `IgnCal.MinMap`, `IgnCal.fi_Max`,
  `IgnTempCal.AirMap` / `EngMap`, `IgnKnkCal.fi_Offset` / `fi_Map1MaxOffset` / `fi_OffsRelMax`,
  `IgnLOffCal.fi_MapOffset`, `IgnOffsCal.fi_Offs` / `fi_OffsCyl` / `DNComp*`, `IgnJerkCal.fi_Tab`,
  `KnkSoundRedCal.fi_OffsMap` — all **0.1° per count**.
- `TorqueCal.fi_IgnLimMap` (0.1°) and `TorqueCal.M_IgnInflTorqMap` (0.1 Nm/°).

Airmass (`mg/c`), rpm, torque (`Nm`) and temperature (`°C`) symbols are 1:1 anyway, so raw and
displayed are the same number.

## 1. WHAT KIND OF ECU THIS IS

Three things define T7 and explain almost every design decision in it:

1. **Mass-airflow based, per-combustion.** The fundamental load unit is **airmass per
   combustion, `mg/c`** (`MAF.m_AirInlet`), not manifold pressure and not a VE model. It comes
   from the hot-film MAF (`In.Q_AirInlet`, g/s) converted with engine speed
   (`Convert_Q_to_m()`). MAP (`In.p_AirInlet`, kPa) is used for diagnostics, boost control,
   and corrections — *not* as the primary load axis.

2. **Torque-structured.** All external interventions (TCM, TCS/ESP, cruise, limiters) are
   expressed in **Nm**, and there is a bidirectional model converting between torque and
   airmass. The driver's pedal is an *airmass request*; torque limits are converted back to
   airmass limits before they act.

3. **Drive-by-wire (E-gas).** There is no throttle cable. The ECU commands throttle **area**
   in mm² (`Out.A_Throttle`). Throttle is a slave actuator that services the airmass request;
   boost control (APC valve) works alongside it. A secondary 592 processor supervises the
   throttle for safety, with a limp-home spring.

**Consequence for tuners:** you do not "add boost" directly. You raise the *airmass request*
and the *airmass limits*; the boost controller then delivers whatever pressure is needed to
achieve that airmass. Fuel and ignition are looked up on the resulting airmass.

| `ST_` | status / enum / boolean | — |
| `N_`, `n_Comb...` | counts (combustions, samples) | 1 |

### Map layout convention

Maps are flat 1-D arrays with **separate axis (support point) arrays**. Naming:

- `...XSP[]` / `x_axis[]` / `m_AirXSP[]` → **X axis**, usually **airmass (mg/c)** or load
- `...YSP[]` / `y_axis[]` / `n_EngYSP[]` → **Y axis**, usually **engine speed (rpm)**
- `Map[16*18]` means **16 rpm rows × 18 airmass columns** (row-major over rpm)

Support points must be **monotonically increasing**. Interpolation is bilinear
(`Misc.app/Source/Interpol.s`). Values are clamped at the axis ends — no extrapolation.

The two dominant grids in T7 are:
- **16 × 18** (16 rpm × 18 airmass) — the "big" grid: fuel, ignition, torque
- **16 × 16** — pedal, throttle-area, knock, injection angle

## 3. TOP-LEVEL SIGNAL FLOW

```
 pedal + cruise + TCM/TCS/ESP + idle + limiters
                    │
                    ▼
        ┌───────────────────────────┐
        │   AIRMASS MASTER          │  arbitration of airmass requests (mg/c)
        │   → AirData.m_Master      │
        └───────────────────────────┘
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
 AIRMASS CONTROLLER      BOOST CONTROLLER
 (throttle area, mm²)    (APC valve PWM %)
        │                       │
        ▼                       ▼
   Out.A_Throttle        Out.PWM_BoostCntrl
                    │
                    ▼  (engine responds)
            MAF.m_AirInlet  ← measured airmass, mg/c
                    │
        ┌───────────┼───────────┬──────────────┐
        ▼           ▼           ▼              ▼
   m_AirInletFuel  ...Ign   ...Boost      ...Torque      (4 differently-filtered copies)
        │           │                        │
        ▼           ▼                        ▼
   FUEL MASTER   IGNITION               TORQUE MODEL
   Out.t_Injection  Out.fi_Ignition     Out.M_Engine
```

**The four filtered airmass copies matter.** `MAF.m_AirInlet` is filtered separately for each
consumer, with different steady-state and transient time constants
(`MAFCal.FilterCFuelSteady` / `FilterCFuelTrans`, `FilterCIgnSteady` / `FilterCIgnTrans`,
`FilterCTorqSteady` / …). Fuel gets a fast filter, ignition a slower one. This is why logged
`m_AirInletFuel` and `m_AirInletIgn` differ during transients.

Filter formula (all of them):
```
filt = old + (100 * (new - old) ± Const) / Const
```
`Const = 100` → 100 % new (no filtering); `200` → 50 % new; `400` → 25 %; `800` → 12.5 %.

### Task rates

Functions are called from fixed-rate tasks and from the **combustion (angle) interrupt**:

- **Angle interrupt** (48° after TDC per cylinder): fuel mass, injection time, knock window
- **10 ms**: airmass controller, throttle area master, boost control
- **20 ms**: pedal line, CAN torque requests
- **50 ms**: engine max-airmass limiter (`LimEng`)
- **100 ms / 1000 ms**: adaption, diagnostics, slow compensations

Per-cylinder fuel factors have their own decimation — `FuelCalcDelay[]` sets how many
combustions between calls to each fuel factor function.

### 4.1 Pedal → driver airmass request (`m_Driver`)

```
             * TorqueProt.X_MBTIgnEffic / TorqueProt.X_IgnEffic
```

| Symbol | Size | Meaning |
|---|---|---|
| `PedalMapCal.m_RequestMap[16*16]` | 16×16 | **The pedal map.** Requested airmass in mg/c |
| `PedalMapCal.n_EngineMap[16]` | | X axis: rpm |
| `PedalMapCal.X_PedalMap[16]` | | Y axis: pedal position, 0.1 % |
| `PedalMapCal.X_AutFacTab[6]` / `v_VehAutSP[6]` | | Speed-dependent pedal gain, automatic |

### 4.2 Airmass master — request arbitration

`Air.app/Source/AIRMASS.C`. Every input is a `{AirMass, Status}` pair; a `Status == 0` input is
inactive and skipped. Order is fixed:

```
m_Driver  ──SELECT HIGH──┐
m_CC      ───────────────┴─> m_A60Out   (DriveMaster: pedal vs cruise)
m_A60Out  ──SELECT LOW ──┬─> m_A201Out  (vs m_Wheel — TCS/ESP wheel-slip limit)
m_A201Out ──ADD ─────────┬─> m_A203Out  (+ m_Idle — idle controller air)
          ── EngTip limit ─> m_A203Out  (tip-in/tip-out clamp, EngTipCal)
m_A203Out ──ADD ─────────┬─> m_A202Out  (+ m_LoadComp — AC, alternator, cold friction)
m_A202Out ──SELECT HIGH ─┬─> m_A204Out  (vs m_nLow  — minimum load / dashpot)
m_A204Out ──SELECT LOW ──┴─> m_Master   (vs m_nHigh — MAX LIMIT, see below)
```

`ECMStat.ST_ActiveAirDem` tells you which stage is currently governing — log it when a car
won't make requested load.

### 4.3 The max-airmass limiter `m_nHigh` — the real "boost limit"

`Air.app/Source/Limeng.c`:

```

```

| Symbol | Size | Meaning |
|---|---|---|
| `BstKnkCal.MaxAirmass[16*16]` | 16×16 | **Max allowed airmass, manual gearbox.** X = knock/ignition offset, Y = rpm |
| `BstKnkCal.MaxAirmassAu[16*16]` | 16×16 | Same, automatic gearbox |
| `BstKnkCal.OffsetXSP[16]` | | X axis: accumulated knock ignition offset |
| `BstKnkCal.n_EngYSP[16]` | | Y axis: rpm |
| `BstKnkCal.DivFacHighLoad` / `DivFacLowLoad` / `DivFacDelTimer` / `NegStep` | | How fast the limit is pulled down on knock and restored after |
| `LimEngCal.TurboSpeedTab[8]` / `TurboSpeedTab2[8]` | | Turbo overspeed protection → `LimEngProt.m_TurboSpeedMaxReq` |
| `MaxSpdCal.n_EngLimAir[5]` / `T_EngineSP[5]` | | Rev-limiter airmass cut-back vs coolant temp |
| `MaxSpdCal.AirOffset`, `RampFac`, `MaxOffset1/2`, `n_FuelCutOffset` | | Rev limiter behaviour and fuel-cut offset |

**This is the map that limits peak boost on a T7.** Raising the pedal map alone does nothing
if `BstKnkCal.MaxAirmass` clamps it. Note the X axis is the *knock ignition offset* — the more
the ECU has retarded for knock, the further left it reads, and the lower the allowed airmass.
That is T7's built-in knock-driven boost taper.

## 5. TORQUE MODEL

`Air.app/Source/Torque.c` + `TORQUE.H`. This is the arbitration layer for every external
torque request. Two directions:

### 5.1 Airmass → torque (what the engine is making)

```
M_Nominal = TorqueCal.M_NominalMap[ rpm, (m_AirInletTorq - m_FrictionAir) ]
```

| Symbol | Size | Meaning |
|---|---|---|
| `TorqueCal.M_NominalMap[16*18]` | 16 rpm × 18 air | **Nominal engine torque, Nm.** The core torque map |
| `TorqueCal.n_EngYSP[16]` | | Y: rpm (shared by all 16×18 torque maps) |
| `TorqueCal.m_AirXSP[18]` | | X: airmass mg/c (shared) |
| `TorqueCal.m_FrictionAir` | | Idle/friction airmass at warm idle, mg/c — subtracted before lookup |
| `TorqueCal.fi_IgnLimMap[16*18]` | | Ignition angle at which retard starts reducing torque, 0.1° |
| `TorqueCal.M_IgnInflTorqMap[16*18]` | | Torque lost per degree of retard, **0.1 Nm/°** |
| `TorqueCal.M_NomCorrMap[16*18]` | | E85 correction matrix → `TorqueProt.M_E85ActCorr` |
| `TorqueCal.X_IgnEfficTab[34]` / `fi_MBTOffsYSP[34]` | | Ignition efficiency vs offset from MBT (feeds the pedal-map scaling in §4.1) |
| `TorqueCal.M_PumpLossMap[2*2]`, `M_FricBase`, `X_EngFricGain`, `X_AirFricGain` | | Pumping and friction loss model |

Actual torque = nominal, reduced by the ignition retard currently applied, via
`fi_IgnLimMap` + `M_IgnInflTorqMap`. Reported as `Out.M_Engine`.

### 5.2 Torque → airmass (how a limit is enforced)

`ConvTorqueAirmass(torque, rpm)`:

```
m_required = TorqueCal.m_AirTorqMap[ rpm, torque ] + TorqueCal.m_FrictionAir
```

| Symbol | Size | Meaning |
|---|---|---|
| `TorqueCal.m_AirTorqMap[16*16]` | 16 rpm × 16 torque | **Inverse map:** airmass needed for a given torque |
| `TorqueCal.M_EngXSP[16]` | | X: torque, Nm |
| `TorqueCal.X_AccPedalMap[16*16]` | | Reverse-engineers a pedal position for `Out.X_AccPedal` sent to TCM |
| `TorqueCal.m_PedYSP[16]` | | Airmass axis for `X_AccPedalMap` |

`m_AirTorqMap` and `M_NominalMap` **must be consistent with each other** — they are inverses.
If you rescale one you must rescale the other, or torque-based interventions become wrong
(harsh or absent gear-shift torque reduction, wrong TCS behaviour, wrong displayed torque).

### 5.3 Torque limits

| Symbol | Size | Meaning |
|---|---|---|
| `TorqueCal.M_EngMaxTab[16]` | 16 | **Max engine torque vs rpm, manual** |
| `TorqueCal.M_EngMaxAutTab[16]` | 16 | Max torque vs rpm, automatic |
| `TorqueCal.M_EngMaxE85Tab[16]` / `M_MaxE85AutTab[16]` | | Same for E85 |
| `TorqueCal.M_5GearLimTab[16]` / `n_Eng5GearSP[16]` | | 5th-gear-specific limit (manual) |
| `TorqueCal.M_ManGearLim[6]` | | Per-gear torque limit, manual gearbox |
| `TorqueCal.M_OverBoostTab[16]` | | Max torque while overboost is active |
| `TorqueCal.EnableOverBoost`, `t_OverBoost`, `t_Cooling`, `M_OverBoostRamp`, `M_OverBoostOffset`, `m_OverBoostLevel` | | Overboost timer/hysteresis |
| `TorqueCal.M_EngTempTab[16]` / `T_LimEngTemp` / `M_IncEngTemp` | | Cold-engine torque limit and ramp-out |
| `TorqueCal.M_EngTempE85Tab[16]` | | Cold-engine limit on E85 |
| `TorqueCal.M_BrakeLimit`, `M_StallLimit` | | Brake-override and brake+throttle stall limits |
| `TorqueCal.M_ReverseTab[3]` / `n_EngSP[3]` | | Reverse gear limit (auto) |
| `TorqueCal.M_NoiseRedLim`, `M_AutNoiseRedLim`, `X_NoiseRedAccP`, `t_NoiseR*`, `v_NoiseRed*` | | Noise-reduction torque cut |
| `In.M_TCMLimitReq`, `In.M_TCSTorqueReq`, `In.M_TCSTotalReq` | | External requests over CAN |

The lowest active limit wins. It is then enforced by, in escalating order:
1. **Air reduction** — limit converted to airmass, applied to `m_Master`
2. **Ignition retard** — down to `TorqueCal.fi_IgnMinTab[2*4]` (min absolute advance vs coolant
   temp `T_EngSP[2]` and rpm `n_EngMinSP[4]`), starting when overshoot > `M_HysIgnRedOn`
3. **Fuel cut** — when overshoot > `M_OffsFCOStart` for `t_DebFuelCut` ms; released at
   `M_OffsFCOStop`

`TorqueCal.T_NoIgnRet` / `T_NoIgnHyst` block ignition retard above a modelled exhaust
temperature (catalyst protection) — retard would raise EGT further.

**Tuning note:** if you raise real engine output without raising `M_EngMaxTab` /
`M_EngMaxAutTab` and the nominal torque maps, the torque master will see the engine
overshooting its own limit and will retard ignition or cut fuel to bring it back. This is the
classic cause of "it pulls, then falls flat".

## 6. FUEL

`Fuel.app/Source/Fuelmast.c`. Called from the angle interrupt, per cylinder, 48° after TDC.
Skipped (previous value reused) if <40 ms since that cylinder's last update.

### 6.1 The chain

```
1.  m_FuelBasic  = MAF.m_AirInletFuel / 14.65          (stoich AFR, petrol)

2.  m_FuelActual = m_FuelBasic × (all multiplicative factors below)

3.  + AdpFuelAdap.AddFuelAdapt        (additive adaption; scaled by
                                       Idle.n_EngineNominal / In.n_Engine below idle)

4.  if not ECMStat.ST_EngineStarted:  m_FuelActual = StartProt.m_FuelActual

5.  t_InjBasic  = m_FuelActual × 600 / InjCorrCal.InjectorConst      [µs]
    (fuelmass in 10 µg units, InjectorConst in g/min)

6.  if not ECMStat.ST_EngineSynced:   t_InjBasic /= 2   (semi-sequential double firing)

7.  t_InjActual = t_InjBasic + InjCorrProt.t_InjBatt    (voltage dead-time comp)

8.  if fuel-cut conditions:           t_InjActual = 0

9.  Out.t_Injection = t_InjActual
```

#### Where closed loop stops — the load window

The three tables are all **airmass in mg/c, 1:1**, indexed on `LambdaCal.RpmSp[16]`, and the
live interpolated values are loggable as `LambdaProt.MinLoad`, `LambdaProt.MaxLoadNorm` and
`LambdaProt.MaxLoadTime`. Closed loop runs only inside the window:

```
airmass < LambdaProt.MinLoad          → open loop  (overrun / very low load)
MinLoad ≤ airmass ≤ MaxLoadNorm       → CLOSED loop, if nothing else disqualifies it
airmass > LambdaProt.MaxLoadNorm      → open loop  (normal condition — this is the boundary)
airmass > LambdaProt.MaxLoadTime, held for LambdaCal.TimeOpenLoop → open loop
```

`MaxLoadTimeTab` is the *timed* ceiling — a load you may briefly exceed before the ECU gives
up on closed loop. In stock calibrations it is set far above `MaxLoadNormTab` (2000 vs
900 mg/c), so **`MaxLoadNormTab` is the threshold that matters in practice**: everything above
it runs open loop, on `BFuelCal.Map` alone. Below it, `Lambda.LambdaInt` is actively correcting
and will hide fuel-map error from you. `LambdaCal.m_MaxLoadHyst` adds hysteresis around the
limit; `MaxLoadE85Tab` replaces `MaxLoadNormTab` on E85.

Closed loop is also dropped for reasons that have nothing to do with load: knock fuel
enrichment active, transient (tip-in) fuel adjustment, fuel cut, coolant temp below
`LambdaProt.MinTempCthr` (closed throttle) / `MinTempOthr` (open throttle), rpm below
`LambdaCal.MinRpm`, sensor or injector faults, and the wait for probe heat-up and
`LambdaCal.MinCombustion` combustions. **`Lambda.Status` is 0 when closed loop is running and
non-zero with the reason code otherwise** — log it rather than guessing why a trim is flat.

#### `AdpFuelProt.MulFuelAdapt` — the long-term trim

A **single global multiplier** on the whole fuel map, not a per-cell correction: one number in
**percent** (txlogger scales it 0.01), `0` = neutral, `+5` = 5 % more fuel everywhere, `−10` =
10 % less. `AdpFuelProt.MulFuelAdapt` is the live value, `AdpFuelAdap.MulFuelAdapt` the copy
persisted in NVRAM. Its additive twin `AddFuelAdapt` does the same job at idle/low load.

It is learned from where `Lambda.LambdaInt` sits, but only inside the
`AdpFuelCal.WMul*` rpm/load window and only when the adaption master lets it run.
**A value that does not move is normal** — the ECU runs its fuel adaption occasionally (in
normal use essentially after a refuel), not continuously. Do not read a "stuck"
`MulFuelAdapt` as a fault or as proof the fuel map is right. It does, however, fight a freshly
changed fuel map until it re-learns or is reset.

Note the T7 wideband sensor value in a log Lambda.External or DisplProt.LambdaScanner **lags the actual combustion by roughly
80 ms** (sensor + transport delay). Do not correlate a log's lambda sample with the same
timestamp's airmass sample.

## 7. IGNITION

`Ignition/Source/Ign.c` and `IGNOFS.C`. Structure: one **absolute base angle** from the active
base map, plus a sum of **offsets**, then clamps.

### 7.1 Assembly order

```
IgnProt.fi_ABS  = active absolute map          (normal / idle / start / gas)
                    │
IgnProt.fi_Offset = IgnTempProt.fi_Offset      (air + engine temp)
                  + DNComp.fi_Offset           (Drive/Neutral)
                  + KnkSoundRedProt.fi_Offset  (knock sound reduction)
                  + IgnKnk.fi_Offset[cyl]      (knock retard, per cylinder)
                  + IgnJerk.fi_Offset          (anti-jerk)
                  + IgnOffsCal.fi_Offs         (global trim)
                  + IgnOffsCal.fi_OffsCyl[cyl] (per-cylinder trim)
                  + knock adaption
                    │
   clamped to IgnKnkCal.fi_OffsRelMax
                    │
IgnProt.fi_Calc = fi_ABS + fi_Offset      (or fi_ABS + IgnLOff.fi_Offset if start map active)
                    │
   min() against the torque model's IgnTorqueAngle  → Ign.ST_TrqIgnActive
                    │
   ramped between functions: IgnCal.fi_RampInc / fi_RampDecMan / fi_RampDecAut
                    │
   clamp low:  IgnCal.MinMap[8*8]  (→ IgnProt.fi_Min), and −10.0° hard floor
   clamp high: IgnCal.fi_Max,      and +45.0° hard ceiling
                    │
Out.fi_Ignition
```

`Ign.fi_OtherOff` is the sum of the temp + D/N + sound-reduction offsets, and is what the
knock-air (`BstKnkCal`) and knock-fuel (`KnkFuelCal`) functions see alongside the knock offset.

## 8. BOOST CONTROL

`Boost.app/Source/Boost.c`. Closed-loop on **airmass request vs achieved**, output is APC
solenoid duty cycle `Out.PWM_BoostCntrl` (0.1 %).

```
PWM = MainConstant + P + I + D

MainConstant = BoostProt.RegConValue      (feed-forward from RegMap)
             + BoostProt.OffsetHighAlt    (altitude comp)
             + BoostProt.OffsetTemp       (air temp comp)
             + BoostAdap.Adaption         (learned)

P = load_difference × f(load_diff, rpm) / 100
I = I + load_difference × f(load_diff, rpm) / 1000
D = load_derivative × f(load_diff, rpm) / 20
```

| `BoostCal.RegMap[128]` | **8 load × 16 rpm** | **Base duty cycle feed-forward.** Axes `SetLoadXSP[8]` × `n_EngSP[16]` |

## 10. CROSS-DEPENDENCIES TO RESPECT

1. **`M_NominalMap` ↔ `m_AirTorqMap` are inverses.** Change one, change the other, or all
   torque-based interventions misbehave.
2. **Raising airmass without raising `M_EngMaxTab`** ⇒ the torque master sees an overshoot and
   pulls ignition / cuts fuel. Symptom: pulls then flattens.
3. **`BstKnkCal.MaxAirmass` X axis is knock retard.** Any knock immediately walks the boost
   limit down. Fix the knock, don't just widen the table.
4. **`BFuelCal.Map`, `IgnNormCal.Map`, `TorqueCal.M_NominalMap` share the 16×18 grid** but
   each has its *own* axis arrays. If you extend the airmass range, extend all of them
   consistently or the maps will be reading different physical points.
5. **`LambdaCal.MaxLoadNormTab` sets where closed loop stops.** Below it, lambda control masks
   fuel-map error. Tune the fuel map above that threshold, then verify below.
6. **`AdpFuelAdap` learned trims persist** and will fight a fresh fuel map until reset.
7. **`MAFCal.Filter*` constants change what the maps *see*.** Two identical maps with different
   filter constants behave differently in transients.
8. **`MapChkCal.CheckSum`** — the cal area is checksummed; the binary must be re-checksummed
   after edits or the ECU will flag it.

## 11. THINGS THIS ECU DOES *NOT* HAVE

- No VE table, no speed-density fuelling (MAP is a correction/diagnostic input only).
- No direct "target boost in bar" table. Boost is emergent from airmass demand.
- No target-AFR table. `BFuelCal.Map` is a *multiplier on stoichiometric*.
- No per-cylinder ignition maps — only per-cylinder *offsets* (`IgnOffsCal.fi_OffsCyl`) and
  per-cylinder knock retard.
- No launch control, no flat shift, no antilag in stock calibration.

| `DisplProt.LambdaScanner` | λ | Wideband via the scanner/development input, converted through `DisplAdap.LamScannerTab1/2/3` (selected by `DisplAdap.ScannerSelect`, axis `AD_ScannerSP[7]`) |
| `Lambda.External` | λ | Wideband from a controller connected to txlogger itself. Arrives ~40 ms late relative to the ECU channels |
| `Lambda.LambdaInt` | % of the base fuel map | Closed-loop short-term trim. **0 = no correction**, +10 = 10 % more fuel, −5 = 5 % less |
| `AdpFuelProt.MulFuelAdapt` | % of the base fuel map | Live long-term multiplicative fuel adaption, same convention: 0 = neutral, −10 = 10 % less fuel. The persisted twin is `AdpFuelAdap.MulFuelAdapt` |
| `MAF.m_AirFromp_AirInlet` | mg/c | Airmass **derived from MAP**, independent of the MAF sensor |

### The three-way airmass comparison

This preset deliberately logs three airmass numbers. Comparing them is the core diagnostic:

```
m_Request                 what the ECU asked for
MAF.m_AirInlet            what the MAF sensor measured
MAF.m_AirFromp_AirInlet   what the MAP sensor implies
```

- **`m_Request` > `m_AirInlet`, sustained** → the engine cannot deliver the request. Boost
  controller saturating (`PWM_BoostCntrl` pinned), or a limiter is *not* the cause because
  limiters lower `m_Request` itself. Look at hardware: wastegate, leaks, restriction.
- **`m_Request` capped flat below what the pedal map should give** → a limiter is active.
  Check `ECMStat.ST_ActiveAirDem`, then `BstKnkCal.MaxAirmass` (with `IgnProt.fi_Offset` as its
  X input), `TorqueCal.M_EngMaxTab`, `LimEngCal.TurboSpeedTab`, `MaxSpdCal`.
- **`m_AirInlet` ≠ `m_AirFromp_AirInlet`** → the two sensors disagree. A boost leak after the
  MAF reads high on MAF / low on MAP; a failing MAF reads low on MAF / normal on MAP. T7's own
  boost diagnostic (`Boosdiag.cpp`) uses exactly this comparison.

### `ActualIn.` vs `In.` — a real difference

`ActualIn.X` is the raw converted sensor value. `In.X` is what the control functions actually
consume, after:
- **limp-home substitution** — if `LimpActive.X` or `Fault.X` is set, `In.X` becomes the fixed
  `LimpIn.X` value while `ActualIn.X` keeps showing the real (bad) sensor;
- **for `p_AirInlet` only**, subtraction of the learned offset `OBDAdap.p_AirInletComp`.

So `ActualIn.p_AirInlet − In.p_AirInlet` = the learned MAP offset. If a log shows a sensor
value frozen at a suspiciously round number in `In.` but moving in `ActualIn.`, that sensor is
in limp-home.

### Other gotchas when reading these logs

- **Wideband lag.** `DisplProt.LambdaScanner` lags the combustion that produced it by roughly
  **100 ms** (sensor response + exhaust transport). Never correlate a lambda sample with the
  same-timestamp airmass sample — shift it back before judging a tip-in lean spot.
- **`MAF.m_AirInlet` is the unfiltered master copy.** Fuel actually uses `m_AirInletFuel`,
  ignition uses `m_AirInletIgn` — differently filtered (§3). During transients the logged
  channel is not the number the fuel map was indexed with.
- **`IgnProt.fi_Offset` bundles everything.** A steady −2° at cold start is light-off
  (`IgnLOffCal`), not knock. A steady offset at high IAT is `IgnTempCal.AirMap`. Only spiky,
  load-correlated retard is knock. Add `IgnKnk.fi_Offset` / per-cylinder channels if you need
  to separate them.
- **`Out.fi_Ignition` is post-clamp.** If it flatlines while `IgnProt.fi_Offset` keeps moving,
  you have hit `IgnCal.MinMap` or `IgnCal.fi_Max`.
- **`Lambda.LambdaInt` freezes in open loop.** Above `LambdaCal.MaxLoadNormTab` there is no
  correction — a flat 0 % at high load means "not controlling", not "perfect". `Lambda.Status`
  tells you which it is.

### Channels worth adding

`In.X_AccPedal` (real driver pedal), `Out.M_Engine` and `Out.M_MaxAtActualRPM` (torque vs its
limit — shows torque interventions directly), `Out.t_Injection` (injector duty headroom),
`BstKnk.MaxAir` (the live boost-limit value), `Torque.ST_FuelCutReq`, `Torque.ST_ExtTrqLim`,
`ECMStat.p_DiffThrot`, `Knock.*` per-cylinder counters.

## 13. ANSWERING STYLE

- Always give the fully-qualified symbol (`BstKnkCal.MaxAirmass`, not "the boost limit map").
- Quote values **in the scale the tool gave you**, with the unit ("1.12 on `BFuelCal.Map`",
  "17.5° on `IgnNormCal.Map`"). Only mention raw counts when the symbol is unscaled
  (`scale = 1`) and the internal resolution matters — then spell it out: "175 raw = 17.5°".
- Never convert a tool value before quoting it, and never propose a `show_map_diff` value in a
  different scale than `read_symbol` printed for that map.
- Name the axis arrays when discussing a map.
- When recommending a change, name the downstream clamp that could nullify it.
- Distinguish `...Cal` (flashable) from `...Prot`/`...Adap`/live (observation only).
- If asked about a symbol not listed here, say you're not certain it exists in this calibration
  rather than guessing at its function.
